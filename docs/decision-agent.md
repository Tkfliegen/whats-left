# Production Decision Agent backend

`POST /api/analyze/decision` is backend only. It is not connected to the dashboard;
the current illustrative Decision UI and timing remain unchanged.

## Contracts and model

Exact shared types: `src/types/decision.ts`. `DecisionRequest` reuses the existing
DecisionGateRequest and adds validated `leaks: LeakResult` and
`decision_gate: DecisionGateResponse`. It contains Evidence, Scenario output,
calculator output and the authoritative Gate. No Notes or upstream input
reconstruction is accepted. Response: `{ decision: DecisionResult }`.

The strict JSON output schema is exported as `decisionSchema` from
`src/app/api/analyze/decision/decision.ts`. All objects require every specified
property and disallow additional properties; textual output fields require
nonempty strings. Recommendation includes type, candidate_id, title, rationale.
Comparison includes candidate_id, target_leak, scenario_status, assessment,
verified_impact and currency. Priorities include source_type, key and
why_it_matters. Confidence is low/medium/high.

Nebius: `https://api.tokenfactory.nebius.com/v1/chat/completions`;
`nvidia/nemotron-3-super-120b-a12b`; temperature 0.2; max_tokens 2000;
`chat_template_kwargs: { enable_thinking: false }`; strict json_schema named
`decision_agent_v1`; native server fetch with 60-second timeout and no-store.
Only server-side NEBIUS_API_KEY is used. There are no automatic retries.

## Input boundary

Validate upstream structure and exact Scenario/Simulation joins using existing
Gate request validation. Gate candidate values, currencies, periods, readiness,
missing inputs and non-ready context must agree with supplied upstream outputs.
Confirmed leaks must match scenario/non-ready coverage. Check policy enums and
Gate state/reason consistency. No threshold, financial impact or ranking is
recomputed in this layer. Only source values are compared for equality.

The Gate is an authoritative upstream input; this endpoint does not independently
re-rank or prove that its supplied top/gap was originally generated by trusted
code. A future server orchestrator must retain trusted upstream provenance;
structural cross-checks are not cryptographic authenticity or a substitute for
Scenario authorization/financial verification.

Malformed/unsupported input returns HTTP 400. Missing key returns safe HTTP 500.
Provider failures, refusals, truncated/invalid JSON, exposed reasoning fields or
thought tags, schema failures and deterministic validation failures return safe
HTTP 502. Invalid provider results are never logged, returned, retried or repaired.

## Narrow model input

`buildDecisionInput` supplies Gate permission, gap status, top ID, candidate
records with authorized scenario definitions, non-ready context, upstream
missing inputs, policy-required categories, leak titles/categories/confidence,
and evidence confidence. Aggregate revenue/costs and arbitrary Notes are not
sent. There is no task to compute a gap or financial outcome.

The projection includes a recommendation_contract and comparison_sources. These
provide exact source fields BEFORE inference, including a nonempty collect-data
title and explicit null-ID non-ready rows. They do not repair model output.
The model adds short rationale/assessments, selects grounded priority sources,
and supplies qualitative confidence. Priority options include short safe
why_it_matters wording describing only the input's decision role.

## Deterministic output validation

- Gate needs_more_data/no_actionable_scenario: needs_more_data + collect_data,
  recommendation candidate_id null. Never business_action.
- Gate action_allowed: actionable + business_action, exactly the authoritative
  top_candidate_id, calculable candidate, and exact supplied scenario title.
- Every candidate and non-ready item appears exactly once in comparison. No
  unknown IDs, duplicate rows, omissions, changed target/status/impact/currency.
- Non-ready rows use null candidate_id, impact and currency.
- Priority keys exactly match the declared source type: upstream missing strings
  or Gate policy categories. No unknown or duplicate source/key pairs.
- Non-action responses require at least one grounded priority except the
  documented no-source/no-action exception below.
- No silent edits, recalculation, reassignment, additions or deletion of rows.

## Empty-source handling

If no_actionable_scenario has no explicit upstream missing category, allow
priority_inputs empty. The model explains that no authorized action or explicit
missing category was supplied; it cannot fabricate a category.

A needs_more_data Gate with neither upstream missing inputs nor policy-required
sources cannot satisfy the production collect-data contract. Reject the request
with HTTP 400 before any provider call. This includes currently ungrounded
currency/period/zero-impact blocking states unless a future structured input
contract supplies an appropriate source. Do not invent a request to fill them.

## Conservative free-text guards

Normalized phrase-level guards cover service disruption, production shortage,
product/service quality, service levels, employee/customer impact, training
requirement, and known unsupported ROI/risk/ease/strategic-advantage assertions.
Use Unicode normalization, word boundaries and explicit phrase variants, not
substring matching or embeddings. A phrase supplied in the model's authoritative
input is not categorically banned. Exact harmless statements such as
`No service disruption is asserted.` are allowed; they do not exempt a separate
assertion in another sentence.

A separate conservative numeric-presence guard rejects new numeric prose,
unprovided monetary amounts, and unsupplied multiples or percentage-point
expressions. ID digits are excluded as numeric permission; a supplied headcount
or waste-rate digit cannot authorize an invented financial impact. Numeric and
currency formatting is normalized without financial arithmetic. Structured
financial fields must always equal the original Gate values.

These guards are NOT full semantic truth verification. Synonyms, number words,
causal claims and misuse of already-supplied concepts may escape a bounded
filter; benign unrecognized wording may also be rejected. Future expansion
requires deliberate tests rather than loosening validation to improve pass rate.

## Live verification

Basic tests use the actual Next endpoint. Reliability tests use the unchanged
production POST handler in an isolated temporary HTTP server to capture raw
provider metadata without introducing production logging. Each request makes
one fresh model call. All failures and preliminary alignment attempts are
reported separately; no invisible retry or post-response repair is performed.
